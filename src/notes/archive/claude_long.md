## What is this project?

**zimr** — a Zig port of a subset of raylib (and imgui), targeting
`wasm32-wasi` + WebGL2.  No emscripten, no C dependencies; output is
a wasm binary plus a small JS runtime.

Most-recent finished sub-project: **rlsw**, a pure-Zig software
renderer originally lifted from raylib's `rlsw.h` (lives in
`src/rlsw.zig`).  Era IV closed at turn 117; see
`src/notes/rlsw-plan.md` for the full per-turn history and the
"What shipped end-to-end" rundown at the bottom.  Paired with
`src/renderer_trait.zig` (a `gl: anytype` trait + adapters that lets
one scene-drawing function drive both rlgl and rlsw) and
`examples/rlsw_side_by_side.zig` (the dual-pipeline A/B demo
with cursor-driven divider + perf bar + pixel-diff overlay).

Check `PLAN.md` for the current active sub-project, if any.

## Reference sources

Upstream source trees for the libraries zimr ports from / draws
from are referenced throughout this codebase by the conceptual
names below.  Read them when you need to compare behavior against
the reference, port a new function, or check a convention:

- **raylib** — raylib's C source.  zimr ports a subset; this is
  the authoritative reference for any `rl*` / `Draw*` / texture /
  model behavior.  The cheatsheet generator parses headers from
  here.
- **imgui** — Dear ImGui's C++ source.  Reference for `ui.zig`'s
  widget semantics (button, slider, combo, child windows, etc.).
- **mr_ecs** — the reference ECS implementation the archetype
  code in `src/entities.zig` was lifted from.  Use when porting
  ECS features or reasoning about archetype layout / component
  dispatch.
- **three.js** — three.js source.  Useful for 3D algorithm
  references (camera math, material shaders, glTF parsing) —
  three.js's implementations are well-tested and the source is
  readable.

**Where these actually live in the sandbox.**  Day-to-day work
does NOT need a copy of the upstream source.  The cheatsheet
generator reads the vendored snapshot at
`scripts/data/upstream_index.json`, which captures every public
API the cheatsheet cites.  That index is the only thing the
build depends on.

The full upstream source trees only need to be extracted when
**refreshing** the vendored index (running
`scripts/refresh_upstream_index.py` after raylib or imgui
releases a new version).  In that case the convention is:

- `/tmp/raylib-master/` — raylib upstream source
- `/tmp/imgui-master/`  — Dear ImGui upstream source

`refresh_upstream_index.py` reads from those paths and writes
`scripts/data/upstream_index.json`.  No other script touches
`/tmp/`.

Don't treat these reference sources as authoritative for *zimr's*
API — zimr's public surface is whatever `src/notes/CHEATSHEET.md`
documents.  The reference sources are for reading/learning during
porting work, not for direct copying without an explicit port turn.

## Per-turn rules (non-negotiable)

These are the rhythm of every turn.  Skipping any of them is a
process bug.

### 1. Save zip every turn — UNCONDITIONALLY

Last action of every turn is to save a **per-turn-named** snapshot.
This is unconditional: the zip is saved **even if the tree does
not compile, even if tests crash, even if the turn was pure docs,
even if the work feels half-done**.  The snapshot is the only way
the user has to recover a turn-in-progress — skipping it because
"it's not green yet" loses real work.  Always save, then describe
the state honestly in the turn summary.

```sh
cd /home/claude/work && \
  rm -f /mnt/user-data/outputs/zimr-turn-<N>.zip && \
  zip -rq /mnt/user-data/outputs/zimr-turn-<N>.zip . \
  -x "zig-out/*" ".zig-cache/*" ".git/*" "node_modules/*"
```

`<N>` is the current turn number — `zimr-turn-208.zip`,
`zimr-turn-209.zip`, etc.  Then call the `present_files` tool with
the path so the user can download it.

**Save a `-pre` snapshot BEFORE any large mechanical sweep**
(turn 342 rule).  When a turn will run an autofixer, bulk
sed/regex, structural rewrite, or anything that touches >20
sites in one shot, save `zimr-turn-<N>-pre.zip` FIRST, then
do the sweep.  If the sweep corrupts the tree (turn 341 had
a Python autofixer break brace counts in codecs.zig + ui.zig),
the `-pre` snapshot is a one-line restore: unzip the specific
broken files from it, keep the sweep's good fixes everywhere
else.  Without a pre-snapshot the only recovery is to revert
from the source zip and lose every prior fix — turn 341 lost
~336 sites' worth of work that way.  Cost of a -pre snapshot
is ~2s of zip time; the payoff is enormous when the script
blows up somewhere.

**Snapshot cleanup rule (apply every turn, no need to ask, no need
to confirm the user downloaded anything).**  The
`/mnt/user-data/outputs/` directory accumulates these snapshots and
gets large (each is ~15-20 MB).  After saving the current turn's
zip, prune old ones by this rule:

- **Keep every snapshot whose turn number is a multiple of 5.**
- **Keep the 5 most recent snapshots**, regardless of number.
- **Delete everything else.**
- **`-pre` snapshots follow their parent turn.**  Keep
  `zimr-turn-<N>-pre.zip` exactly as long as you'd keep
  `zimr-turn-<N>.zip`.  Prune them together.

Worked example — at turn 243, the surviving snapshots are:
`..., 215, 220, 225, 230, 235, 239, 240, 241, 242, 243`
(the multiples of 5 going back indefinitely, plus 239-243 as the
five most recent; 240 satisfies both).

This is a standing authorization: delete the old snapshots without
asking, as long as the rule is followed exactly.  Only ever delete
`zimr-turn-*.zip` files — never the standalone `.html` builds, the
`*-plan.md` exports, or `zimr.zip`, which are distinct artifacts,
not superseded snapshots.

### 2. CHANGELOG entry every turn

Changelogs live in `src/notes/changelogs/`, **one file per ten
turns**: `changelogNNN-MMM.md` where `NNN` is the decade start and
`MMM` the decade end — `changelog210-219.md`, `changelog220-229.md`,
etc.  (The two oldest files predate the scheme and carry wider
ranges: `changelog001-092.md` and `changelog093-199.md`.)

The **active** file is the highest-numbered one — the only file
with a `## [Unreleased]` header.  It is **prepend-only**: after
`## [Unreleased]`, add a new `### Turn N — ...` block.  The entry
shape is fixed:

- A brief narrative paragraph (what happened, why).
- **Code shipped** — bullet list of concrete changes.
- **Implementation choices** — decisions worth remembering.
  Capture the "considered X, chose Y because Z" reasoning where
  it's not obvious.
- **Tests added** — count delta (e.g. `+18, total 942 → 960`).
- **Audit numbers** — see "Audit gate" below; pin the actuals.
- **Files touched** — bullet list including LOC delta where
  meaningful.
- **Next turn** — one sentence saying what's next.

**Watch out for the `## [Unreleased]` header eating bug:** when
prepending an entry via `str_replace`, the `replace` operation can
silently swallow blank lines around the previous turn's heading.
After every changelog edit, run (against the active file):

```sh
grep -nE "^### Turn" src/notes/changelogs/changelog<NNN-MMM>.md | head -10
```

and verify the recent entries are in descending order with no gaps.
If a heading is missing, restore it via a follow-up `str_replace`.

**Rolling over to a new decade file.**  When the first turn of a
new decade opens (turn 220, 230, ...), that turn's entry does NOT
go in the old file.  Instead, the same turn:

```sh
# Freeze the file just completed: drop its `## [Unreleased]` line
# (it's a frozen archive now — edit the header preamble to say so,
#  matching the sibling frozen files).
# Then create the new active file:
#   src/notes/changelogs/changelog<NNN-MMM>.md  with
#   - a short preamble naming the turn range + pointing at siblings
#   - the `## [Unreleased]` line
#   - just THIS turn's entry
```

The per-decade split keeps every file small enough that a fresh
session reading "the last 2-3 entries" never has to open a
megabyte of history.  No size-threshold rotation anymore — the
turn number alone decides when a file closes.

### 4. Audit gate every turn

**Compile errors → `zig build test`.  Always.  No exceptions.**

This is the single command for finding compile errors during
iteration.  It runs host unit tests AND typechecks every example
(via `addObject` steps wired into `test_step` in `build.zig`) AND
every test root, in ~7s warm.  No other command should be reached
for to surface compile errors:

- ❌ NOT `zig build install` — that's the production wasm build,
  ~3min warm.  25× more cost for the same compile errors.
- ❌ NOT `zig build smoke-test` — that depends on `install` and
  then *runs* every example in a browser harness, slower still.
- ❌ NOT `zig build math-test` — that's only the vendored zmath
  test suite, misses everything else.
- ✅ `zig build test` — host tests + example typecheck + test
  roots.  Surfaces every compile error the production build would,
  ~7s warm.  Iterate against this until clean.

Once `zig build test` is green, *then* run the full audit gate
below for the slower checks (style, smoke, install, globals, DAG).

```sh
cd /home/claude/work
zig build test --summary all      # host tests + example typecheck — the inner loop
zig build lint-check              # fmt-check + AST linter (style gate; turn 343)
zig build smoke-test              # wasm smoke; expect 86/86 PASS, 0 FAIL today
zig build install                 # full wasm build; clean output
python3 scripts/count_globals.py  # 0/0/0
python3 scripts/check_dag.py      # only the allowlisted ui ↔ zimr SCC
```

**The style gate is `zig build lint-check`.**  Composite step that
runs `zig fmt --check` + the AST linter together; fails if either
does.  Use it in CI, in `build_everything.bat`, and as the
pre-push check.  Default `zig build` is NOT gated on style — fast
iteration matters more than implicit checks, especially during
multi-turn cleanup arcs when the linter is intentionally noisy.
The linter currently exits 0 (warn-only) and prints a detailed
note about each rule the first time that rule fires per run
(turn 344) so the WHY of every flag is visible without opening
this file.  When the cleanup arc completes, the linter's exit
code flips to nonzero and `lint-check` becomes a hard gate.

For fmt-only checks (e.g. when the linter is too noisy to read
during cleanup):

```sh
zig fmt --check src/ examples/ build.zig tools/
```

Not exposed as its own `zig build` step — `lint-check` is the
canonical gate and a separate `fmt-check` step would be redundant.

**Smoke focus shortcut.**  The full smoke runs all examples
headlessly (~70s, dominated by per-example startup, not
compilation).  When iterating on a specific arc you can
restrict to just the relevant examples and drop wall time to
~1-2 seconds:

```sh
zig build smoke-test -Dfocus=ui_tables_demo            # single example
zig build smoke-test -Dfocus=ui_tables_*               # prefix glob
zig build smoke-test -Dfocus=ui_tables_*,ui_drag_drop_*  # multiple
```

The `*` suffix is a literal char in the pattern, matched as a
prefix.  Plain entries match exactly.

**Discipline.** `-Dfocus` is the default during per-turn iteration
on one arc.  Run the FULL unfocused suite **once every 3 turns at
most**, or at arc close — not every turn.  Reasons:

1. The full suite is a ~70s wall-clock cost; on a 5-10 minute turn,
   running it every iteration eats a meaningful fraction of the
   turn budget.
2. **Full smoke rebuilds every wasm in DEBUG mode**, clobbering any
   ReleaseSmall artifacts in `zig-out/web/`.  Running smoke and
   then `python3 scripts/build_standalone.py X` without an
   intervening `zig build install --release=small` produces a
   4×-bloated standalone.  `build_standalone.py` now self-heals
   (forces a release rebuild before reading the wasm), but that
   rebuild is wasted work if the previous turn already had a clean
   release build.

**ALWAYS pass `--release=small` to smoke-test too** so it doesn't
clobber the install:

```sh
zig build smoke-test --release=small -Dfocus=<arc>   # focused, ~1s warm
zig build smoke-test --release=small                 # full, ~14s warm
```

Without `--release=small`, smoke triggers a full Debug rebuild of every
example (~3-4 min cold) and clobbers the ReleaseSmall artifacts.  With it,
the same content-addressed cache serves install + smoke + standalone —
all warm at <2s after the initial cold build.

The right cadence:
- **Every turn:** `zig build test` only.  ~7s warm.  This catches
  compile errors and runs all host unit tests.  Do NOT run smoke-install
  every turn — it's the heavyweight check, not the inner loop.  Only
  the test step is mandatory each turn.
- **Every 3rd turn**, **at arc close**, or **before saving a zip you'll
  ship as a visual-verify deliverable**: `zig build smoke-test
  --release=small` (focused via `-Dfocus=<arc>` if you're iterating on
  one area; full unfocused otherwise).
- **When in doubt about cross-arc impact** (touched `runtime.zig`,
  `rlgl.zig`, `drawing.zig`, or anything else many examples depend on):
  run the full unfocused suite that turn, even if it hasn't been 3
  turns.
- **When user reports a visible bug in a specific example**:
  rebuild + smoke that example via `-Dfocus`, then build the standalone
  and `present_files` it.

## Stable failures are not baselines

When `zig build test` reports `1295/1301 passed (6 skipped, 13
crashed)` and that count doesn't move turn-to-turn, the easy
mistake is to treat the count as a stable baseline and stop
asking what's behind it.  A stable failure count isn't a
baseline — it's just a number you've memorized.  Real baselines
are *understood* failures: each one has been investigated, its
cause documented, and the decision to leave it failing is
deliberate.

Two examples from the api-flatten arc that this rule would have
caught earlier:
- 13 crashes called "pre-existing rlgl tests with `batch=undefined`"
  for ~5 turns.  Turned out to be a real bug (the tests never
  allocated the heap-only `VertexBuffer` after rlsw moved off
  inline storage in turn ~95).  Once investigated, fixed in 30
  minutes; brought test count from 1282 → 1295.
- 6 skips called "rlsw Y-flip cleanup pending" since turn 120.
  Turned out to be straightforward Y-coordinate updates per test
  (signed area for cull_back; corner-color positions for
  gradient quads; pixel y for line endpoints).  Once investigated,
  fixed in one turn; brought test count from 1295 → 1301.

The pattern in both cases: a deferred-cleanup comment, an
obvious workaround (`return error.SkipZigTest` / "use undef and
hope"), and a stable-but-unsatisfying count that lived on after
the original author moved to other work.  When a comment says
"pending," it's not pending if no one's coming back.

When in doubt, the question to ask is: *what would I have to do
to make this pass?*  If you can answer in a couple of paragraphs,
do it instead of leaving the count.  If you can't, document the
real blocker, not just the symptom.

`zig fmt` is opinionated and idempotent.  Two behaviors worth
internalizing:

- **Trailing commas force multiline.**  This is the main lever you
  have for keeping lines under 120 chars (Rule 10).  A trailing
  comma after the last argument of a fn signature, fn call, struct
  literal, or array literal tells `zig fmt` "break this onto
  multiple lines, one item per line."  Without the comma, `fmt`
  packs everything onto one line — even past 120 chars; it does
  NOT auto-wrap.

  ```zig
  // No comma → fmt keeps on one line, even at 142 chars.
  pub fn drawRect(ctx: *Ctx, rect: Rect, fill: Color, border: Color, border_width: f32) void {

  // Add a comma after the last param → fmt breaks onto lines.
  pub fn drawRect(
      ctx: *Ctx,
      rect: Rect,
      fill: Color,
      border: Color,
      border_width: f32,
  ) void {
  ```

  When fixing a Rule 10 violation, the trailing-comma trick is
  almost always the right tool.

- **`// zig fmt: off` / `// zig fmt: on`** preserves manual layout
  exactly inside the block.  Useful for matrix literals where
  the visual grid carries information.  Use sparingly — most
  alignment we'd want is normal Zig source and `fmt` should
  apply.

`zig fmt` does NOT enforce Rule 10.  It just stops fighting you
when you add commas.

Document the actuals in the CHANGELOG entry under "Audit numbers".

zip — the user shouldn't see a regressed zip.

## Style guide (inline)

These rules are mandatory for all new code and all modified code.
Existing code that doesn't match is grandfathered until touched;
the moment you edit a function, bring the whole function up to
spec.

### Rule 1 — function declaration arguments

The default is **one argument per line**, with a trailing comma on
the last arg so `zig fmt` keeps it that way.  Two exceptions:

1. **Single-argument fns** stay on one line.
2. **Two-argument fns** may stay on one line *if* the whole signature
   fits under 80 columns.

Three or more arguments **always** break to multiple lines, regardless
of total length.  The split improves diff-ability (one arg per line
means each line touches at most one parameter) more than the saved
vertical space matters at three args.

```zig
// Good — single argument on one line.
pub fn deinit(self: *Mock) void { ... }

// Good — two args, signature fits under 80 cols.
pub fn fade(c: Color, alpha: f32) Color { ... }
pub fn checkCollisionRecs(a: Rectangle, b: Rectangle) bool { ... }

// Good — two args but signature is long, break it.
pub fn loadImageFromMemory(
    gpa: std.mem.Allocator,
    bytes: []const u8,
) errors.LoadError!Image { ... }

// Good — three+ args, always break.
pub fn genMeshCube(
    gpa: std.mem.Allocator,
    width: f32,
    height: f32,
    length: f32,
) std.mem.Allocator.Error!Mesh { ... }
```

Closing `)` sits on its own line at the same indent as the opening
`pub fn`; return type follows on that same line.

The "two-arg single-line" carve-out exists because pairs like
`(c: Color, alpha: f32)` read better as one line — there's nothing
to scan, the two args are obviously related, and breaking to four
lines (open, arg, arg, close + ret) adds vertical noise.  Three or
more args is where readers actually need the vertical separation.

### Rule 2 — local variables declare their types explicitly

Even when Zig can deduce the type, write it.  **Reason: greppability.**

```zig
const i: usize = someFunc();
const name: []const u8 = "hello";
var counter: u32 = 0;
```

**Exception:** skip the annotation when the type is already
mentioned on the same line — allocations, casts, typed function
calls already carry the type as a search anchor.

```zig
const verts = try gpa.alloc(f32, n);     // alloc(f32, ...) is the anchor
const i = @as(usize, @intCast(raw));     // @as(usize, ...) is the anchor
```

Other exceptions: captured iteration variables (`for (xs) |x|`)
and pattern-bound errors (`catch |err|`) — types come from the
iterator/error set and writing them is awkward.

### Rule 3 — braces required on every branch

Even single-statement bodies of `if`/`else`/`while`/`for` get
braces.  No exceptions.

```zig
if (count == 0) {
    return;
}
while (i < n) : (i += 1) {
    sum += data[i];
}
```

### Rule 4 — comments are casual, undecorated, unnumbered

Top-of-function `///` doc comments describe *what the function is
for* and any non-obvious contracts (allocator ownership, error
conditions).  Inline `//` comments inside the body explain *why*
something is the way it is.

Skip the comment entirely when the function name already says it.
No banner decorations inside functions; no numbered steps.  Module-
level `// ====` section dividers ARE allowed.

### Rule 5 — array-of-N-copies via `@splat`

```zig
const buf: [32]u8 = @splat(0);
const fill: [N]Color = @splat(.{ .r = 0, .g = 0, .b = 0, .a = 255 });
```

Mandatory — `@splat` is the only path; the array-repetition `**`
operator was removed from the language.  Use `@splat` everywhere,
including for byte buffers and string-shaped arrays.

### Rule 6 — argument clarity at call sites

A reader looking at a function call should be able to tell what
the arguments mean from the call alone, or from the immediately
surrounding lines.  When the meaning isn't self-evident, lift the
arguments into named locals.

```zig
// Bad — what do 35 and 4 mean?
drawCapsule(35, 4);

// Good — the locals tell the reader.
const height: f32 = 35;
const radius: f32 = 4;
drawCapsule(height, radius);
```

The signal that you should lift: **bare numeric or boolean literals
at the call site**, magic constants embedded in struct literals, or
any argument whose role you can only figure out by opening the
function definition.  When the same magic constant appears at two
or more call sites, the lift is mandatory.

### Rule 7 — keep boolean conditions trivial

`if`/`while` conditions stay as simple as possible.  Avoid stacking
multiple `and`/`or` clauses, especially when one clause does work
(a function call, an arithmetic comparison, a chain of field
accesses).  Lift each non-trivial sub-expression into a named bool
first.

```zig
// Bad.
const hovered: bool = opts.enabled and pointInRect(ctx.input.mouse_pos, rect);

// Good.
const ptr_in_rect: bool = pointInRect(ctx.input.mouse_pos, rect);
const hovered: bool = opts.enabled and ptr_in_rect;
```

For three or more clauses, prefer separate `if`s with early returns,
or a labelled `blk:` block with `break :blk` exits.  The rule of
thumb: if you'd add a comment explaining the condition, you should
be lifting clauses into named bools instead — the bool name *is*
the comment.

### Rule 8 — single-call helpers earn their keep

When a helper is called from exactly one place, ask:

1. Is the name doing real work?  `clampToScreen(rect)` earns its
   place — the name *is* documentation.  `processStep1(...)` does
   not.
2. Does it read or write state the caller doesn't?
3. Is the body more than ~10 lines AND each chunk is genuinely
   separable?

If two of three answers are "no", inline it.  Don't extract
pre-emptively — write code inline first; lift to a helper when a
*second* caller appears.

### Rule 9 — no module-level mutable globals (anywhere)

Don't write `var foo: T = ...;` at module scope.  This applies to
**every `.zig` file in the codebase** — `src/`, `examples/`,
tests, everywhere.  Mutable state belongs on a struct that's
owned, allocated, and passed explicitly.

```zig
// Bad — module-level var, anywhere in zimr code.
var scratch_buf: [4096]u8 = undefined;
var counter: u32 = 0;

// Good — fields on a state struct, passed where needed.
const State = struct {
    scratch_buf: [4096]u8 = undefined,
    counter: u32 = 0,
};
```

**Allowed exceptions: 2 module-level vars, both at C-ABI seams.**

The wasm/JS bridge can't carry context arguments — exports called
by the JS runtime are stateless C functions, so they reach a
module-private singleton to find their target.  Same for `pub
export fn` shims that JS event handlers call (DOM events, frame
ticks).  When this constraint applies, the global is justified;
otherwise it isn't.

Current allowed globals:

1. `src/zimr.zig`: `var bridge: Bridge = .{};` — wraps `active_app`
   (the live `*App` for `zimr_frame` to find) and the four
   `default_*_browser` instances (process-wide loader/clock/rng/
   logger fallbacks used when no App is active or the user hasn't
   overridden via `App.setLoader` etc.).  All zimr-layer C-ABI seam
   state lives in this one struct — adding new bridge fields means
   extending `Bridge`, not declaring a new `var`.

2. `src/runtime_assembly.zig`: `pub var app: ?*Runtime = null;` —
   the live `*Runtime` for the `pub export fn input_push_*` shims
   that JS DOM events call.  Lives at the runtime layer, separate
   from zimr's bridge, because the DAG layering keeps `zimr →
   runtime_assembly` as a clean forward edge.

3. `src/entities.zig`: `var counter: std.atomic.Value(u32) = ...;`
   (inside `pub const world_stamp = struct { ... };`) — mints
   unique per-world debug stamps across the whole process lifetime.
   Atomic because worlds can be created from any test or example;
   reset-on-restart is fine because handles don't persist across
   restarts.  Allowlisted by the linter via exact (file, name)
   match (turn 340).

4. **One-shot warning flags** — module-level `var warned_X: bool =
   false;` is the idiom for "fire this log warn ONCE per process
   lifetime, no matter how many UiContexts come and go."  Moving
   it to per-context state would re-fire per ctx, defeating the
   purpose.  Allowlisted by the linter via `warned_*` name prefix.
   See `drawing.zig`'s `warned_text_no_font` for the canonical
   example.

**No other module gets a module-level `var`.**  When you find
yourself reaching for one, the principle to apply: *the function
signature must be unable to carry the state*.  C-ABI callbacks
without `user_data` qualify.  Anything you can route through a
`*State` / allocator / explicit parameter does not.

The function-scoped `struct { var X = ...; }` idiom is a HIDDEN
global — it doesn't trip `count_globals.py` but it's still shared
mutable state across every invocation of the enclosing fn.  Use
it ONLY when capturing closure state for a C-ABI callback whose
signature can't be widened (the two examples in `src/runtime.zig`
test bodies).  When the function signature can take an extra
pointer, take it instead.

**For examples specifically**, use `z.run` — it allocates state
from `gpa` and dispatches each frame with a typed pointer.

```zig
pub export fn main() void {
    z.run(.{ .window = ... }, State, initState, update) catch |err| {
        std.debug.print("run failed: {s}\n", .{@errorName(err)});
    };
}

fn initState(gpa: std.mem.Allocator, f: *z.Frame) !State { ... }
fn update(f: *z.Frame, state: *State) void { ... }
```

If init is genuinely trivial:

```zig
fn initState(_: std.mem.Allocator, _: *z.Frame) !State {
    return .{};
}
```

**Scratch buffers** (clipboard staging, format-string holding
areas, etc.) live on State, not at module scope.  Even
"obviously stateless" buffers should be fields — they make
ownership obvious, test setup uniform, and the diff between
"this is owned per-instance" and "this is shared process-wide"
clear at a glance.

**Constants** at module scope are fine: `const ITEMS_PER_PAGE:
usize = 50;` is not state.  The rule is only about `var`.

### Rule 10 — keep code lines under 120 characters

Hard limit: 120 columns in `.zig` files.  Soft target: most lines
well under that.  The reason isn't the screen — it's that wide
lines almost always mean too much is happening on one line, and
the right fix is the fix you'd want anyway (lift a sub-expression
into a named local, break a function signature across lines per
Rule 1, split a chained method call across `.` boundaries).

```zig
// Bad — 142 columns, two ideas crammed onto one line.
const visible = ctx.frame_count > 0 and self.state.contains(.visible) and rect.intersect(viewport).hasArea();

// Good — each idea on its own line; reads top-to-bottom.
const has_started: bool = ctx.frame_count > 0;
const flag_visible: bool = self.state.contains(.visible);
const overlaps_viewport: bool = rect.intersect(viewport).hasArea();
const visible: bool = has_started and flag_visible and overlaps_viewport;
```

```zig
// Bad — fn signature stretches off-screen.
pub fn drawRectFilledWithBorder(ctx: *Ctx, rect: Rect, fill: Color, border: Color, border_width: f32, rounding: f32) void {

// Good — Rule 1 fixes this AND the line length.
pub fn drawRectFilledWithBorder(
    ctx: *Ctx,
    rect: Rect,
    fill: Color,
    border: Color,
    border_width: f32,
    rounding: f32,
) void {
```

The rule applies to code files (`.zig`, `.js`, `.ts`, build
scripts).  **Markdown documents are exempt** — prose, tables, and
ASCII-art diagrams have their own readability rhythm; forcing
120-column wrapping on tables especially makes them harder to
edit, not easier.  Wrap markdown prose to whatever width feels
natural for the editor; ~70-90 columns is typical.

When you find yourself wanting to exceed 120 in code, the answer
is almost always one of:

1. **Add a trailing comma to the offending list** (fn signature,
   fn call, struct literal, array literal).  `zig fmt` will then
   break it across lines, one item per line.  Most 120-char
   violations are this — see "Audit gate" above for examples.
2. A Rule 6 lift (named locals).
3. A Rule 7 split (separate `if`s).

### Rule 11 — integer-type discipline

zimr targets wasm32 exclusively.  On that target, `c_int = i32`
and `c_uint = u32` *as named types* — same bit width, but Zig
treats `c_int` and `i32` as the same type, while `c_uint` and
`usize` are distinct (even though both are 32-bit on wasm32).

**Default integer types for new code:**

| Type    | When to use                                                |
|---------|------------------------------------------------------------|
| `i32`   | Signed default.  Pixel coords, signed sizes, deltas, etc.  |
| `usize` | Non-negative default.  Indices, counts, lengths, frame counters. |
| `i64`   | When the range genuinely exceeds ±~2 billion.              |

**Never use** `c_int` or `c_uint` in zimr Zig code.  They carry
"this is a C type" baggage that's irrelevant since zimr is pure
Zig — exceptions only for the JS-bridge `extern fn` declarations
in `web.zig` where the C-type naming is meaningful, and even
those should be wrapped in zimr-native pub fns.

**`u32` is acceptable for one thing:** opaque 32-bit handles that
flow through from graphics or audio APIs — `Texture2D.id`,
`Shader.id`, `Sound.handle`, GL `prog`/`vao`/`vbo`/`fb` IDs,
`sample_rate`.  These are conceptually "an opaque ID from the
underlying API," not a Zig-side count or index.  When in doubt,
prefer `usize`.

**Avoid `u64` in public surfaces.**  Almost any value bigger than
±2 billion is a byte count or time stamp, both of which read
better as `i64` (signed; negative means "before t=0" or "error
sentinel").  Internal storage is your call.

Smaller bit widths (`u8`, `u16`, `i8`, `i16`) stay legitimate for
packed/storage contexts: color channels, audio samples, glyph
indices, packed flag bytes.

Inside fn bodies, anything goes — short-lived locals can be
whatever bit width helps the math.  Just don't leak non-blessed
types into a `pub fn` signature.

### Rule 12 — don't read a variable in the same literal that overwrites it

Zig fills an aggregate literal in place, field by field — it does
not build a complete temporary first (unlike a C compound
literal).  So in `v = .{ .a = f(v), .b = g(v) }`, the `.b`
expression sees the *already-overwritten* `.a`.  When a later
field depends on a value an earlier field clobbered, the result
is silently wrong.  Capture the inputs into `const` locals first:

```zig
// Bug — .z reads the .x that was just overwritten.
v = .{ .x = c * v.x - s * v.z, .y = v.y, .z = s * v.x + c * v.z };

// Good — capture first, then build the literal from the locals.
const x = v.x;
const z = v.z;
v = .{ .x = c * x - s * z, .y = v.y, .z = s * x + c * z };
```

### Rule 13 — `extern struct` only at real FFI seams

`extern struct` requires every field to be C-ABI-compatible.
`@Vector(N, T)` is not — it's a SIMD type with non-C alignment.
Putting `@Vector` (directly or via an alias like `Vec`/`Mat`) into
an `extern struct` produces a layout neither Zig nor C fully
agrees on; the result is silent memory corruption at runtime (in
zimr's case: wasm OOB).  Discovered in turn 248 when `Camera3D` /
`Transform` / `Ray` / `BoundingBox` had to be flipped to plain
`struct` after `Vector3` became `zmath.Vec`.

**Use `extern struct` only when the type genuinely crosses a
C-ABI seam** — passed by value through a `pub export fn` or
`extern fn`, or memory-overlaid by JS at known field offsets.
For zimr today, **no struct crosses such a seam by value** (every
FFI export is scalars only); JS only reads byte buffers through
explicit pointer + length.  So `extern` is almost always
vestigial / raylib-fidelity.  When in doubt, use plain `struct` —
Zig's auto-layout is `@Vector`-aware and correct.

If a struct's field types might ever become `@Vector` (Vector2,
Vector3, Vector4, Quaternion, Matrix all may), prefer plain
`struct` proactively so the eventual flip doesn't reintroduce the
UB.  Camera2D already follows this pattern (turn 248) even though
Vector2 is still a struct today.

### Rule 14 — no `xxxEx` function pairs

raylib's C API has `fooEx` companions to many `foo` functions
("Ex" = "extended", meaning "more arguments").  Don't carry that
pattern over to zimr.  When you'd reach for a second function to
add an option, take an options struct instead:

```zig
// Bad — raylib-style xxxEx pair.
pub fn drawCircle(c: Vector2, r: f32, color: Color) void { ... }
pub fn drawCircleEx(c: Vector2, r: f32, color: Color, segments: u32) void { ... }

// Good — one function, options struct with defaults.
pub const DrawCircleOpts = struct {
    segments: u32 = 36,
};
pub fn drawCircle(c: Vector2, r: f32, color: Color, opts: DrawCircleOpts) void { ... }

// Callers:
z.draw.drawCircle(pos, 10, .red, .{});               // defaults
z.draw.drawCircle(pos, 10, .red, .{ .segments = 8 }); // override
```

Why: extending an Ex pair eventually produces `fooExEx`,
`fooExEx2`, `fooExWithFlags`, etc., each duplicating the previous.
An options struct extends without breaking callers and keeps the
function count flat.  Discovered turn 340; linted by
`[ex-variant]` (rule 14).

### Rule 15 — named-struct-init: use `.{}` when LHS declares the type

When the LHS of an assignment, a return slot, a function-call
arg, or any other position already declares the struct type,
the initializer should be `.{...}`, not `Foo{...}`.  The named
form is just noise.

```zig
// Bad — the type is on both sides.
const c: Color = Color{ .r = 255, .g = 0, .b = 0, .a = 255 };

// Good — the LHS already says it's a Color.
const c: Color = .{ .r = 255, .g = 0, .b = 0, .a = 255 };

// Bad — `colorToU32` takes a Color.
const argb: u32 = colorToU32(Color{ .r = 0, .g = 0, .b = 0, .a = 255 });

// Good.
const argb: u32 = colorToU32(.{ .r = 0, .g = 0, .b = 0, .a = 255 });
```

The linter detects this through transparent wrappers: `try`,
`orelse`, `catch`, `if-else`, grouped parens.  It does NOT
recurse into struct fields (so `Foo{ .bar = Bar{} }` doesn't fire
on the inner Bar — only the outer Foo, and only if there's an
unambiguous type signal on the LHS).  Linted by
`[named-struct-init]` (rule 15).  Added turn 340.

### Thin-frame contract (turn 162+)

The `Frame` is a 5-field pure-data struct.  Zero methods, no
runtime-managed state.  Anything stateful the app needs lives on
the user's `State`.

```zig
pub const Frame = struct {
    gl: *rlgl.GlState,
    input: *input.InputState,
    window: *const core.WindowState,
    time: *const core.TimeState,
    audio_device: *audio_device.AudioDeviceState,
};
```

What this means for new code:

- **No `f.X()` calls.**  Every operation is a free function.
  - `z.gl.beginDrawing(f.gl)` + `z.gl.endDrawing(f.gl)` bracket
    every update.  Even examples that don't `clear` still need
    both — otherwise the rlgl batch never flushes.
  - `z.gl.clear(f.gl, color)` instead of `f.clear(color)`.
  - `z.camera.beginMode3D(f.gl, cam)` + `z.camera.endMode3D(f.gl)`,
    same for Mode2D, TextureMode, ShaderMode, BlendMode,
    ScissorMode.

- **No effects on Frame.**  Logger, Loader, RNG live on State as
  a Browser-shape pair:

  ```zig
  const State = struct {
      log_browser: z.runtime.effects.logger.Browser = .{},
      log: z.Logger = undefined,
      // ... in init:
      // s.log = s.log_browser.logger();
  };
  ```

  Unbound Browser = silent/no-op.  Bind a TraceLog to route
  through `dom.log`.

- **Owned per-frame scratch.**  When formatting strings or
  building transient buffers, the State carries
  `scratch: std.heap.ArenaAllocator` and resets it at the top of
  update.  No `f.scratch`.

- **Owned font cache + shapes texture.**  `font_cache:
  z.text.FontCache = .{}` + `shapes_texture:
  z.shapes.ShapesTextureState = .{}` on State; `loadFontDefault`
  in init.  These zero-initialize cleanly and lazy-load on first
  draw.

- **Stash `gpa` for late allocations.**  If `update` allocates
  (e.g. `updateModelAnimation`, ECS spawn paths), stash
  `gpa: std.mem.Allocator` on State and use `state.gpa`.  Don't
  try to thread `gpa` through `update`'s signature.

- **`gpa` is the first init arg.**  `fn initState(gpa:
  std.mem.Allocator, f: *z.Frame) !State` — never read
  `state.gpa` in init; just use the arg directly.  Underscore the
  unused side (`_:` for unused `f` or `_:` for unused `gpa`).

- **Init init bodies don't reference `s` before it's declared.**
  If init needs the font cache to render an image, load the font
  into a local `font_cache` first, build the image, then move the
  cache into the returned State.

- **Helpers thread state explicitly.**  Top-level helpers that
  draw take explicit `&font_cache`, `&shapes_texture` params,
  not implicit `state.X`.

- **Gestures: user ticks.**  No auto-update from the runtime.
  `z.gestures.update(&state.gestures, f.input, f.time)` at the
  top of every update for examples that use them.

- **gallery / multi-pane:** no `subFrame`.  Each sub-app gets
  explicit `&font_cache`, `&shapes_texture`, RNG, logger params
  threaded by the host.  Scissor regions clip per-pane output.

The README and `examples/` are the canonical references for the
shape.  `src/notes/archive/thin-frame-plan.md` has the design
history.

### Process notes (misc)

- **Allocator-taking functions get a leak test in
  `src/leak_test.zig`.**  `std.testing.allocator` catches leaks
  automatically; pattern is "do thing N times in a loop under
  `std.testing.allocator`."
- **The DAG check (`scripts/check_dag.py`) allowlists exactly one
  SCC: `ui ↔ zimr`.**  Anything else means a new cycle was
  introduced.  If a new cycle appears legitimately, update the
  allowlist in the script with a comment explaining why.
- **The globals check (`scripts/count_globals.py`) must report
  `0/0/0`.**  Module-level `var` is forbidden; use `z.run` and
  pass state through.
- **CHANGELOG entries can be massive — don't worry, that's
  intended.**  The CHANGELOG doubles as a per-turn journal; future
  Claudes scan only the most recent entries.
