# S1.4.5b sampler-DSL derisk findings

This session: probed the S1.4.5b "inline-SPIR-V-asm sampler DSL" path
hands-on and discovered the originally-planned approach has structural
issues that would extend the 1-2 session estimate to 4-6 sessions.
Then surfaced a cleaner alternative (GLSL post-process) and proved
it end-to-end.  **Recommendation: go with the post-process design.**

## The original plan was: inline SPIR-V asm for samplers

From `zig-shader-pipeline-plan.md` §0.8:

> The path forward is all-inline-asm: build a `Sampler2D` shadermath
> helper that wraps `OpTypeImage` + `OpTypeSampledImage` +
> `OpImageSampleImplicitLod` in asm strings, decorated with
> `DescriptorSet` + `Binding`.  Scoped as S1.4.5b — 1-2 sessions.

## What we tried + what we learned

### Probe 0 (baseline)
Trivial FS with no asm → clean GLSL output.  Pipeline works.

### Probe 1 (empty asm)
`asm volatile ("" : : : .{ .memory = true })` → compiles.  Asm
channel is open.  Note: the `: "memory"` syntax from x86 fails;
spirv arch wants `.{ .memory = true }` per `lib/std/builtin/assembly.zig`
line 3114 (the "else" packed-struct branch).

### Probe 2 (OpNop)
`asm volatile ("OpNop" : : : .{ .memory = true })` → compiles, .spv
grows ~3 KB, spirv-opt strips it, spirv-cross emits clean GLSL with
no trace.  **Real SPIR-V instructions go through asm.**

### Probe 3 (sampler type declaration in asm)
Inline asm with `OpTypeImage` + `OpTypeSampledImage` declarations
inside a function body → compiles successfully.  BUT:
- Types declared at function scope are technically illegal SPIR-V
  (sampler types should be at module scope)
- spirv-val complains about an unrelated dead `Target_Cpu` struct
  (the known issue spirv-opt's `--skip-validation` flag handles)
- spirv-opt dead-strips all the asm because no variable references it
- Output GLSL has no trace of our sampler types

**This is the central problem**: Zig asm bodies emit at function
scope, but SPIR-V samplers must be at module scope.  Even if we
got past that, we'd need to materialize a variable that Zig's type
system can pass around — and Zig has no type that maps to SPIR-V's
sampled-image.

### Probe 4 (loose uniforms baseline)
`extern const my_texture: u32 addrspace(.constant)` →
`uniform uint my_texture` in GLSL.  This is the S1.4.5 step-1
pattern that already works — and it's the key insight for the
alternative design.

### Probe 5 + 6 (post-process design)

Author the shader with samplers as placeholder u32 loose uniforms:

```zig
extern const albedo_sampler2d: u32 addrspace(.constant);

noinline fn __sample2d(handle: u32, uv: Vec2) Vec {
    return Vec{ uv[0], uv[1], @as(f32, @floatFromInt(handle)), 0.0 };
}
```

Compile through the pipeline (**skip spirv-opt** because `-O` inlines
the helper and destroys the call structure).  spirv-cross emits:

```glsl
uniform uint albedo_sampler2d;

highp vec4 __sample2d(uint _30, highp vec2 _31) {
    return vec4(_31.x, _31.y, float(_30), 0.0);
}

void main() {
    color = __sample2d(albedo_sampler2d, frag_uv);
}
```

Apply 3 regex rewrites in `shader_post.zig`:

```
Rule 1: uniform uint (\w+)_sampler2d;
     -> uniform sampler2D \1;

Rule 2: highp vec4 __sample2d(uint X, highp vec2 Y) { ... }
     -> highp vec4 __sample2d(mediump sampler2D X, highp vec2 Y) {
            return texture(X, Y);
        }

Rule 3: \b(\w+)_sampler2d\b -> \1   (call sites)
```

Output: clean, valid GLSL ES 3.0 with real `sampler2D` uniforms and
`texture()` calls.  **Demonstrated end-to-end this session.**

## The recommended design (refined S1.4.5b spec)

### Authoring convention
Samplers declared with `_sampler2d` / `_sampler3d` / `_samplercube`
suffix:

```zig
extern const s_albedo_sampler2d: u32 addrspace(.constant);
extern const s_normal_sampler2d: u32 addrspace(.constant);
extern const s_env_samplercube: u32 addrspace(.constant);
```

The `s_` prefix is a separate convention so the post-rewritten
identifier (`s_albedo`) doesn't collide with local variables that
might also be called `albedo`.

### `shadermath` API additions
```zig
pub noinline fn __sample2d(handle: u32, uv: Vec2) Vec { ... }
pub noinline fn __sample3d(handle: u32, uvw: Vec3) Vec { ... }
pub noinline fn __sampleCube(handle: u32, dir: Vec3) Vec { ... }
```

Bodies are placeholder math — only the shape matters; the post-
process rewrites them entirely.  Authors call them as
`zm.__sample2d(s_albedo_sampler2d, uv)`.

### Build pipeline changes
- For sampler-using shaders, skip `spirv-opt -O` (or build a custom
  pass list excluding `--inline-entry-points-exhaustive`).
- Add a `post_process_samplers` step in `src/shader_post.zig` that
  applies the 3 regex rewrites.
- Convention: shaders ending in `_fs.zig` get the post-process
  unconditionally (idempotent if no samplers present).

### Trade-offs vs. inline-asm path
- ✅ Tractable: 1 focused session vs 4-6 for SPIR-V asm wizardry
- ✅ Robust: textual surgery on stable structures (uniform decls,
   function decls, identifiers) rather than fragile SPIR-V graph
   manipulation
- ✅ Strong precedent: `rewriteMatUniforms` already does this kind
   of post-process for mat4-vs-vec4[4]
- ⚠ Loses spirv-opt's inlining + cross-function optimization for
   shaders that use samplers.  For a typical fs (pbr_fs is ~167
   LOC) this is unlikely to matter on phone GPUs.
- ⚠ Sampler helpers are not type-safe at the Zig level (handle is
   `u32`).  Acceptable — the Zig-side type safety we'd get from
   inline-asm samplers would be largely cosmetic anyway because
   you can't construct one outside the shader.
- ⚠ Naming convention burden — samplers need a recognizable suffix.
   Minor.

## Open questions for the implementation session

1. Build-pipeline integration: should `addShader` in `build.zig`
   accept a flag like `.has_samplers = true` that switches to the
   sampler-friendly path?  Or always run the post-process and
   always skip `spirv-opt` for `_fs.zig`?
2. Custom spirv-opt pass list: can we get dead-code elimination
   without inlining?  Investigate `spirv-opt -h | grep -i inline`
   for the specific pass to exclude.  If yes, keep optimization
   on for non-sampler shaders.
3. Multi-texture validation: does the rewrite correctly handle
   shaders with 5+ samplers (pbr_fs has 8)?  Probable yes —
   nothing in the design scales worse than O(n).

## CORRECTION + RESOLUTION (second derisk pass)

The "skip spirv-opt" claim above was OVER-SIMPLIFIED.  Skipping
`spirv-opt -O` entirely leaves the Zig stdlib's dead `Target_Cpu`
struct in the SPIR-V, which then forces `#extension
GL_EXT_shader_explicit_arithmetic_types_int8 : require` into the
GLSL output.  **WebGL2 does NOT have Int8 extensions** — the
resulting GLSL won't compile in the browser.

**Real fix**: use a custom spirv-opt pass list that does dead-code
elimination but DOES NOT inline.  The standard `-O` recipe includes
`--inline-entry-points-exhaustive` which kills the `noinline` Zig
helper.  We want everything EXCEPT inlining:

```
spirv-opt \
    --eliminate-dead-functions \
    --eliminate-dead-variables \
    --eliminate-dead-const \
    --eliminate-dead-code-aggressive \
    --skip-validation
```

Verified by probes 8, 9, 10:
- Target_Cpu stripped (no Int8 extensions in output)
- `noinline` helper preserved as a real GLSL function
- 5 samplers all preserved through the limited pipeline
- Identifier names preserved (don't add `--strip-debug`)

**End-to-end WebGL2 acceptance test built**: `sampler_derisk_test`
example loads the rewritten 5-sampler GLSL via
`loadShaderFromMemory` on the actual wasm runtime.  If the HUD
shows green "WEBGL2 ACCEPTED" on phone, the design is fully
derisked.  If red "WEBGL2 REJECTED", there's still a structural
issue in the post-processed GLSL we missed.

Also discovered: `noinline` does NOT survive `spirv-opt -O` even
though the SPIR-V Function spec has a DontInline decoration.  The
optimizer treats DontInline as a hint only — `--inline-entry-points-exhaustive`
ignores it.  So our "skip the inline pass" approach is mandatory,
not just preferable.

## Remaining unknowns to probe before/during implementation

1. **Browser acceptance** — pending Simon's phone test of
   `sampler_derisk_test.html`.  The single biggest remaining
   unknown.
2. **cube samplers + 3D samplers** — only 2D probed.  Likely
   trivial extension (separate suffix, separate helper function).
3. **Vertex-shader samplers** — rare in practice, but check.
4. **Interaction with UBOs** — does the limited-pass spirv-opt
   work for shaders that mix UBOs + samplers?  Likely yes
   (different decorations) but verify before pbr_fs migration
   (which uses both).
5. **DescriptorSet/Binding decorations** — currently the GLSL
   output has no explicit binding annotations.  WebGL2 doesn't
   require them (uses `glGetUniformLocation` + `glUniform1i`).
   For Vulkan compat we'd need them, but zimr is WebGL2-only so
   probably fine.
6. **Real pbr_fs complexity** — 167 LOC + 8 samplers + math.
   The probes used 5 samplers; pbr_fs is bigger.  Likely
   fine but a real conversion will surface any edge cases.

## ✅ GREEN-LIGHT CONFIRMATION

Simon ran `sampler_derisk_test.html` on phone.  HUD: **"POST-PROCESSED
GLSL: shader.id=23 (WEBGL2 ACCEPTED)"** in green.

The post-processed 5-sampler GLSL compiled and linked in real WebGL2
on Chrome/Android.  Every link in the chain confirmed:

```
.fs.zig
   │ zig build-obj -target spirv32-vulkan -O ReleaseFast
   ▼
.spv
   │ spirv-opt --eliminate-dead-{functions,variables,const,code-aggressive} --skip-validation
   │   (NO -O, NO --strip-debug)
   ▼
.opt.spv
   │ spirv-cross --version 300 --es
   ▼
.glsl (with `uniform uint X_sampler2d` placeholders + noinline `__sample2d`)
   │ post_process_samplers: 3 regex rewrites
   ▼
.glsl (with real `uniform sampler2D X` + `return texture(H, UV);`)
   │ loadShaderFromMemory -> WebGL2 glCompileShader + glLinkProgram
   ▼
program id 23 → real GPU shader ready to bind
```

S1.4.5b is now a **1-session implementation arc with high confidence.**
