Native bootstrap

Everything a Windows computer executes for examples/hello_world_owned_main/hello_world_owned_main.zig, from the moment the program is started until the first line of its update runs — told in order, as one thread's journey. Nothing is skipped on purpose: where a step is a library or a driver doing a thousand things, the page says what those things are and moves on; where it is zimr's code or Zig's, the lines are shown.

The program is a hello world that owns its main: the file you write is the root of the program, the first code of yours runs as soon as Zig's start code is done, and from there it is your main that brings up the engine, hands it your functions, and starts the frames. Nothing of zimr's stands between Zig and you — so every step on this page is one your program asked for.

It is meant to be read with the program paused in a debugger beside it, one step at a time. Chapter 0 sets the breakpoint, on the earliest line of source the process runs; every chapter after it says where the debugger should be, and asks a few questions with two answers each. Read only, you can usually guess the answer; stepping, you can see it.

0. Set a breakpoint first

Everything below happens in a fraction of a second. To follow it, stop the program at its very beginning and walk it forward yourself. Four steps:

  1. Build the debug program. Debug is the default mode, and it is the one this page follows: 
    zig build hello-world-owned-main -Dplatform=windows
    This leaves zig-out/windows/hello_world_owned_main.exe and, beside it, hello_world_owned_main.pdb, the debug information that maps machine code back to source lines.
  2. Open Zig's own start code. The first line of source that runs in the process is not in zimr: it is in the standard library that came with your Zig, lib/std/start.zig. zig env prints where that library is (its lib_dir). With the compiler this page was written against: 
    zed C:/dev/zig-x86_64-windows-0.18.0-dev.753+1420479be/lib/std/start.zig:572
  3. Put a breakpoint on line 572, the first line of WinStartup: 
        if (builtin.cpu.arch.isX86() and builtin.abi == .gnu) asm volatile ("fninit");
    (Click in the gutter left of the line number.) Nothing earlier can take a breakpoint: before this line, only Windows' code has run, and Windows ships no source for it.
  4. Start the debug scenario Debug: hello-world-owned-main (windows) (Zed's debug panel, or VS Code's Run and Debug; both are generated into .zed/debug.json and .vscode/launch.json). It launches the exe under CodeLLDB with two settings that matter: the native PDB reader, without which Zig's frame names come out garbled, and fast stepping off, without which stepping over z.loadFont crashes LLDB.

The keys, the same in Zed and VS Code:

Three conventions for the rest of the page:

  • Each chapter opens with a box, In the debugger, saying where you should be stopped and how to get there. Sometimes that is F10 and F11 from where the last chapter left you; sometimes it is a breakpoint to set and F5 — there are loops of thousands of iterations on the way, and stepping through them teaches nothing.
  • F10 runs everything a line calls. On most lines that is what you want. On a few it is the rest of the program — the most important one is start.zig:582, where F10 runs the program until its window is closed. The boxes warn at those lines.
  • A skipped block can flash its last line. When an if is false, F10 may stop for one step on the last line of the block it skips — the jump over the block is attributed to that line — before landing after it. Line numbers are those of the tree this page was written from; when the code moves, they drift, and the quoted line is what to look for.

2. Before the first instruction

In the debugger. Stay paused on start.zig:572 for the whole chapter. Everything here happened before that line, in Windows' code, which has no source to step through. So instead of stepping, this chapter runs three small experiments: one in the debugger, two in a PowerShell terminal opened in the repository's root.

When you start a program, Windows does three things before any of its code runs:

  1. it reads the file, whose header says what the program needs;
  2. it maps the file into memory, with every DLL (library) the header names, and theirs;
  3. it starts a thread, which jumps to the address the header gives as the entry point.

You are paused at the end of step 3. We will look at the three in reverse, starting with what is already on your screen.

Experiment 1: who called us

Look at the call stack panel. The frame on top is where you are. The frames under it are the code that called it — and that is still waiting for it to return, which, for these, will be never.

Checkpoint 2.1. Which frame is directly below the top one?
(a) kernel32.dll`BaseThreadInitThunk
(b) main
answer

(a). The stack has exactly three frames: ours on top, then BaseThreadInitThunk in kernel32, then RtlUserThreadStart in ntdll. main has not been called yet — it is several calls in our future.

Checkpoint 2.2. Which DLL holds the bottom frame — the code every thread on Windows starts in?
(a) ntdll.dll
(b) kernel32.dll
answer

(a). ntdll.dll`RtlUserThreadStart. ntdll is the one DLL in every process; Windows' loader, which did steps 1 and 2, lives in it too.

That is step 3: a new thread started in RtlUserThreadStart, which called BaseThreadInitThunk, which called the entry point — the function you are paused in. Where did the address of that function come from? From the file.

Checkpoint 2.3. What are the file's first two characters?
(a) MZ
(b) PE
answer

(a). Every Windows executable still begins with an MS-DOS header — MZ are the initials of Mark Zbikowski, who designed the DOS format — followed by a tiny DOS program whose only job is to print the sentence you can read on the right. The real header is further on.

Where further on? The DOS header keeps the answer in the four bytes at offset 0x3C: 78 00 00 00. x86 stores numbers least significant byte first (little-endian), so those bytes are the number 0x00000078.

Checkpoint 2.4. Look at offset 0x78 (row 00000070, column 08). What is there?
(a) 50 45 00 00 — PE and two zero bytes
(b) 4D 5A — a second MZ
answer

(a). The PE signature. The two bytes after it, 64 86, read backwards, are 0x8664: the machine, x86-64. Then 07 00: the file has 7 sections (code, read-only data, data, and so on).

Counting bytes by hand gets old quickly, so let PowerShell read the fields that matter. Each line prints one:

$pe = [BitConverter]::ToInt32($exe, 0x3C)
$opt = $pe + 24
'machine     0x{0:X}' -f [BitConverter]::ToUInt16($exe, $pe + 4)
'entry RVA   0x{0:X}' -f [BitConverter]::ToUInt32($exe, $opt + 16)
'image base  0x{0:X}' -f [BitConverter]::ToUInt64($exe, $opt + 24)
'subsystem   {0}' -f [BitConverter]::ToUInt16($exe, $opt + 68)
'stack MiB   {0}' -f ([BitConverter]::ToUInt64($exe, $opt + 72) / 1MB)

$pe is the 0x78 you found; the optional header — not optional at all in an executable — starts 24 bytes after it. The output, for the build this page was written from:

entry RVA   0x124470
image base  0x140000000
subsystem   3

  • image base: where the image would like to be. (Experiment 3 shows where it actually is.)
  • stack: the main thread's stack is reserved at this size, 16 MiB, and committed a page at a time as it grows.

Checkpoint 2.9. The header asked for image base 0x140000000. Where did hello_world_owned_main.exe actually load (line [ 0])?
(a) somewhere else, chosen by Windows, like 0x00007ff609670000
(b) at 0x140000000, as asked
answer

(a). Address space layout randomization (ASLR): Windows chooses where images go, at random, so that an attacker cannot know where their code is. That is why the header gives the entry point as an RVA, an offset. Check it: the base ends in 0000, so base + 0x124470 ends in 4470 — and the stop line says ...44b2, 0x42 bytes into the entry function. Those 66 bytes are the function's prologue, the instructions before its first line; one of them is andq $-0x10, %rsp, which realigns the stack. You will meet the reason in the next chapter, in callconv(.withStackAlign(.c, 1)).

What did not happen

One thing more ran before your line, and one thing — which a C++ programmer would expect — did not.

What ran: thread-local storage. A threadlocal var needs a fresh copy per thread, and on Windows it is the loader that makes them, from a template the image describes. Zig's standard library writes that description itself (lib/std/os/windows/tls.zig, an IMAGE_TLS_DIRECTORY named _tls_used), since there is no C runtime of ours to do it; the loader read it in step 2.

What did not: static constructors. In a C++ program, the C runtime would now run every global object's constructor, in an order nobody can quite predict, before main. Zig has none. Every global in this program — zimr_app, the window struct, the input queue — has its initial value computed at compile time and stored as bytes in the image's .data section, which the loader simply mapped. pub var zimr_app: z.App = .{}; is not a constructor call; it is bytes, already right. So the line you are paused on really is the first thing the program does.

Checkpoint 3.1. What name does the call stack give the top frame — the function you are stopped in?
(a) WinStartup
(b) wWinMainCRTStartup
answer

(b). The debugger names the code by its symbol in the image, and the @export above gave WinStartup the symbol wWinMainCRTStartup. The source is WinStartup; the binary only knows the exported name.

Line by line:

  1. callconv(.withStackAlign(.c, 1)) — not a line that runs, but a promise about the stack. The function is told to assume its stack is aligned to only 1 byte, so the compiler realigns it on entry. An entry point is reached by a jump from code that owes it nothing, and the realignment makes every function after it safe to assume the usual 16 bytes.
  2. fninit — one instruction. It resets the x87 floating-point unit: Windows leaves it set to 53-bit precision, and the GNU ABI (our -gnu target) expects 64-bit. zimr's math is SSE, not x87, but f80 and some of compiler-rt still use the old unit, and this makes them right.
  3. _ = @import("os/windows/tls.zig"); — runs nothing. Importing the file is what puts the TLS directory of chapter 2 into the image; the line only has to exist. The program is not single-threaded (Zig's standard library assumes it may start threads), so it does.
  4. maybeAttachSignalStack() — returns at once on Windows: a signal stack is a POSIX idea, and the function's own switch says .windows => return,.
  5. maybeEnableSegfaultHandler() — in a debug or ReleaseSafe build, installs the handler that turns a crash into a readable stack trace: 
            windows_segfault_handle = windows.ntdll.RtlAddVectoredExceptionHandler(0, handleSegfaultWindows);
    That is the first call this program makes into the operating system. From here on, a null-pointer read anywhere below prints Segmentation fault at address ... and the stack, instead of vanishing silently. (In ReleaseFast, -Dmode=ship, it is compiled out.)
  6. peb() — one instruction, movq %gs:0x60, .... On x86-64 Windows the gs segment points at the thread's TEB (thread environment block), and offset 0x60 of the TEB holds the PEB, the process environment block: the image's base address, its command line, its environment. Zig reads the command line straight from it — there is no GetCommandLineW call.
  7. RtlExitUserProcess(callMain(...)) — calls callMain, and when it returns (when the window has been closed, long after this page ends), exits the process with its result. WinStartup is noreturn: there is nothing to return to.

Your main takes no parameters, so this third line is the whole function. A 1 × 1 white texture, bound whenever a shape is drawn without one, so that the shader can always multiply by a texture. On Vulkan this one line is the first image the host creates itself (the swapchain's images belong to the presentation engine), the first memory allocation (vkAllocateMemory, device-local), a view, and the first sampler. And it is the first write, which brings in two more firsts. The host's uploads command buffer is begun — the very first vkAllocateCommandBuffers of the run — into which every queue write is recorded, to be submitted ahead of the next frame, as WebGPU orders a queue's writes. And the first staging chunk: a 4 MiB buffer in memory the CPU can write, mapped once for the host's life, into which the four bytes 255, 255, 255, 255 are copied before a copy command takes them to the image. Before that, the new image is cleared to zeros: "new memory reads as zeros", one of the promises.

The engine's bindings

shader_runtime.Resources(EngineSchema).init derives the shaders' bindings from a typed schema rather than from hand-counted numbers: group 0 is a 64-byte uniform buffer (a 4 × 4 matrix, identity for now), group 1 the texture and its sampler. That is a buffer, two bind group layouts and two bind groups — on Vulkan, the engine's first vkCreateBuffer (the staging chunk was the host's), two descriptor set layouts, and a first descriptor pool page (room for 512 sets) from which the sets are allocated.

A ring of 32 projections

        for (&r.ortho_ring_bufs, &r.ortho_ring_bgs) |*buf, *bg| {
            buf.* = wgpu.createBuffer(f.device, .{
                .size = shader.wireSizeOf(EngineSchema.Ubo),

Thirty-two more 64-byte uniform buffers, each with its own bind group. The reason is a WebGPU rule that bit: every queue.writeBuffer lands before the whole submission, so a single uniform written twice in one frame (say, for a render-to-texture pass and then for the screen) has only its last value when either pass runs. A ring gives each pass of a frame its own projection. (The source's comment names the bug it fixed: the zimr516 shader_effects "duplicated grid" glitch.)

Five pipelines

        const blend_modes = [_]wgpu.BlendMode{ .none, .alpha, .additive, .multiply, .premultiplied };

A pipeline layout joining the two groups, then one render pipeline per blend mode — five vkCreateGraphicsPipelines calls, each for triangle lists, the 20-byte vertex of position, texture coordinate and colour, the swapchain's format from chapter 7, and no depth. This is where the driver compiles the SPIR-V to the GPU's own instructions. The alpha-blended pipeline becomes the default.

Room for a frame's geometry

One vertex buffer of 1,048,576 vertices (20 MiB) and one index buffer of 1,572,864 indices (3 MiB), into which every frame's shapes and text are batched. Each is zero-filled on creation, by a command recorded in uploads.

Counted on Vulkan, Renderer2D.init made two shader modules, an image with its view and sampler, 35 buffers, two descriptor set layouts, a descriptor pool, 34 descriptor sets, a pipeline layout and five pipelines — and submitted nothing.
